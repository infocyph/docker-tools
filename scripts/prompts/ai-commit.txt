Content of the Commit Message:
Accurately capture the essence of the changes as reflected by the diff. Mention key changes, affected areas, or notable refactorings. If the diff is empty or contains no changes, output a clear message indicating that there are no changes to commit.

Guideline Adherence:
Ensure that every part of your commit message conforms to the instructions below. Do not include the raw diff content in your commit message; instead, provide a succinct summary.

# Commit Message Guidelines

Adopt a structured approach to commit messages using the Conventional Commits specification and the extended rules below. This format enhances clarity, collaboration, and automation.

## Structure

This is the detailed and complete commit message format:

<gitmoji> <type>(<scope>): <subject> <meta>

<body>

BREAKING CHANGE: <breaking-change>
<footer-header>: <footer-value>
<footer-header>: <footer-value>

## Message Components

### Gitmoji

- Indicates the purpose or nature of the overall change.
- If there are multiple changes, select the Gitmoji based on the highest-ranked or most significant type of change.
- Use the Gitmoji code form only, such as `:art:`, `:rocket:`, or `:sparkles:`.
- Select the code that most closely matches the actual diff.

### Type

Indicates the purpose or nature of the change. It must be one of:

- `feat`: New feature.
- `fix`: Bug fix.
- `docs`: Documentation updates.
- `style`: Code style changes.
- `refactor`: Refactoring code.
- `perf`: Performance improvements.
- `test`: Adding or modifying tests.
- `build`: Changes to build system or dependencies.
- `ci`: CI/CD pipeline changes.
- `chore`: Routine tasks or maintenance.
- `revert`: Reverting a previous commit.

### Scope

- Follows kebab case.
- Specifies the affected area of the codebase.
- If multiple areas are detected, use a short slug that best represents the overall scope.
- Examples: `auth`, `dashboard`, `api`, `frontend`, `backend`.

### Subject

- Concisely summarize the change.
- Prefer 50 characters or fewer; never exceed 72 characters.
- Do not end with a period.
- Use sentence case.
- Use imperative mood: `Fix`, not `Fixed` or `Fixes`.
- Use standard terminology.
- Prefer standard first words based on intent:
  - Add: create a capability such as a feature, test, or dependency.
  - Cut: remove a capability such as a feature, test, or dependency.
  - Fix: correct an issue such as a bug, typo, accident, or misstatement.
  - Bump: increase a version, such as a dependency.
  - Make: change build process, tooling, or infrastructure.
  - Start: begin doing something, such as introducing a feature flag.
  - Stop: end doing something, such as removing a feature flag.
  - Refactor: change code structure without changing behavior.
  - Reformat: change formatting only.
  - Optimize: improve performance.
  - Document: improve documentation.
- Do not put repository-specific markers in the subject, including bug IDs, release tags, issue IDs, Jira URLs, or documentation prefixes.
- The subject must be able to complete this sentence naturally: `If applied, this commit will ...`

### Body

- Wrap at 72 columns where practical.
- Provide additional context or details about the change.
- Explain what changed and why, not how it was implemented.
- Explain background and reasoning rather than implementation mechanics.
- Use bullet points with hyphens or asterisks followed by a single space.
- Apply hanging indentation when a bullet wraps.
- Each bullet should end with a relevant Gitmoji code when appropriate.
- Keep the body focused on material changes from the diff.
- Omit the body when the subject alone is sufficient.

### Footers

Footers are optional metadata for tracking and references. Only include a footer when the diff or supplied context clearly justifies it. Common footer headers include:

- `Author`: Original author of the commit.
- `Acked-by`: Person acknowledging or approving the change.
- `Co-authored-by`: Additional contributor; one line per co-author.
- `Closes`: Issue or bug resolved by the commit.
- `Implements`: Feature or design item implemented by the commit.
- `Reviewed-by`: Reviewer of the change.
- `Refs`: Related issue, bug, or reference without closing it.
- `Signed-off-by`: Developer Certificate of Origin sign-off.
- `Tested-by`: Person who tested the change.
- `Fixes`: Issue or bug fixed by the commit.
- `See`: Related discussion or resource.
- `Reported-by`: Person who reported an issue or bug.
- `Suggested-by`: Person who suggested the change or feature.
- `Part-of`: Larger task, feature, or epic.
- `Depends-on`: Commit or pull request required by this change.
- `Changelog`: Specific note intended for a changelog.

Do not invent footer metadata that is not present in the diff or provided context.

### Breaking Changes

- Use `BREAKING CHANGE:` to signal backward-incompatible changes.
- Clearly describe the impact and any necessary migration steps.
- Include this section only when the diff actually introduces a breaking change.

### Meta

- An optional meta tag may indicate commit status.
- Examples: `#wip`, `#irrelevant`.
- Do not add a meta tag unless it is justified by the supplied changes or context.

## Example

:sparkles: feat(dashboard): Implement drill-down functionality

- Refactor subsystem X for readability :art:
- Add a new feature for user authentication :sparkles:
- Update the README documentation :memo:
- Remove unused files and dependencies :fire:

BREAKING CHANGE: The data format for drill-down events has changed.

Refs: #1234
